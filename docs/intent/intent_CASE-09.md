# Intent CASE-09

Лог интервью: `docs/intent/grillme_CASE-09.md` («№N» — номера ответов в нём). Формулировка задачи:
`docs/sources/CASE-09.md` (процесс, правила П-1–П-4). Пометка «опрос 2026-10-18» —
ответы заказчика при закрытии открытых вопросов (см. Open questions).

## Замысел

Добавить в сервис пакетную подготовку писем с решениями по заявкам: батч запускается
HTTP-запросом, отбирает из БД решённые заявки без записи в протоколе, рендерит по каждой
письмо из общего HTML-шаблона — тема и тело, по каждому решению подставляется дефолтная
фраза из утверждённого юристом списка, — ведёт протокол «какая фраза откуда взята»,
возвращает счётчики и массив готовых писем и материализует письма в `.eml` (источник:
ответ в интервью №1, №4, №5, №8, №9, №14, №15; «Дополнение»; расширение фраз на все
решения — опрос 2026-10-18). Реальная отправка писем — вне задачи (источник: ответ
в интервью №2).

## Зачем

Решения по заявкам уже вычисляются и сохраняются, но клиенту не передаются: формулировка
задачи требует превращать список заявок с решениями в пакет персонализированных писем,
готовых к отправке, с протоколом «какая фраза откуда взята» (источник: формулировка
задачи, процесс; код: db/schema.sql — решения персистятся). Отказ клиенту сообщается
только формулировкой из утверждённого списка, без внутренней причины; список покрывает
все три решения, не только отказы (источник: формулировка задачи П-2, П-3; ответ
в интервью №3, №5; опрос 2026-10-18). Email и ПДн сервис не хранит, поэтому письмо
готовится без адресата, а адрес подставит внешний сервис рассылки (источник: ответ
в интервью №7; код: db/schema.sql — email-полей нет, `applicant_ref` — «синтетический
идентификатор клиента, ПДн не храним»). Идемпотентность «одна заявка — одно письмо»
не дублирует рассылку при повторных проходах (источник: ответ в интервью №9, №11).

## Constraints

- Тело письма — HTML (источник: ответ в интервью №14).
- Один общий шаблон для всех трёх решений; отдельного шаблона для `rejected` нет, текст
  письма определяется подстановками. П-1 формулировки задачи («один шаблон на каждое
  из трёх решений») читаем как «шаблон применяется к каждому из трёх решений»;
  приоритет ответа №4 подтверждён (источник: ответ в интервью №4; опрос 2026-10-18).
- Единый шаблон хранится файлом в репозитории, id шаблона фиксированный
  (источник: ответ в интервью №10).
- Тема письма рендерится тем же единым шаблоном (подстановки как для тела); From —
  фиксированное значение проекта, точное значение фиксируется в plan
  (источник: опрос 2026-10-18).
- Подстановки в шаблон — минимум: id заявки, `applicant_ref`, решение
  (`approve`/`review`/`reject`), при `approve` — одобренный лимит, дефолтная фраза
  из списка для соответствующего решения (источник: ответ в интервью №12; расширение
  фразы на все решения — опрос 2026-10-18). `applicant_ref`, решения и одобренный
  лимит уже сохраняются в БД (источник: код: db/schema.sql).
- Список фраз хранится в БД; редактирует его юрист, система только читает; у фраз есть
  признак активности; список группируется по типу решения, в каждой группе дефолтная
  фраза помечается отдельным флагом (источник: ответ в интервью №3, №11, №13;
  группировка и флаг по каждому решению — опрос 2026-10-18).
- Фраза письма — дефолтная фраза своей группы из утверждённого списка; для отказов
  формулировка берётся только из этого списка; конвертации внутренней причины
  в формулировку нет (источник: формулировка задачи П-2; ответ в интервью №5;
  расширение на все решения — опрос 2026-10-18).
- Внутренняя причина отказа/скоринг в письмо не попадает ни в каком виде, включая
  пересказ (источник: формулировка задачи П-3; ответ в интервью — «Следствия»).
- Протокол «какая фраза откуда взята» хранится в БД, одна запись на заявку
  (источник: ответ в интервью №1, №9). Состав: id заявки, id использованной фразы,
  id шаблона; id фразы обязателен в каждой записи — П-4 буквально, вариант ответа №15
  (id фразы только для `reject`) не применяется (источник: формулировка задачи П-4;
  опрос 2026-10-18).
- Отбор в батч: все заявки статуса `decided`, по которым есть решение и нет записи
  в протоколе; одна заявка — одно письмо (источник: ответ в интервью №9). Статусы
  заявок — `new`/`decided`/`cancelled` (источник: код: db/schema.sql).
- При нескольких решениях по одной заявке в письмо попадает последнее — максимальный
  `created_at`/id (источник: опрос 2026-10-18; код: db/schema.sql — нет уникальности
  по application_id).
- Нет активной фразы в группе решения или не помечена дефолтная: заявки этого решения
  пропускаются без письма и без записи в протоколе, остальные обрабатываются;
  в ответе батча — отчёт о пропущенных; пропущенные попадут в следующий проход
  автоматически (источник: ответ в интервью №11 — про `reject` при пустом списке/нет
  активной фразы; обобщение на все решения и случай «дефолтная не помечена» —
  опрос 2026-10-18).
- Запуск батча — HTTP-запросом (источник: ответ в интервью №8). Ответ батча: счётчики
  (обработано / пропущено по причинам) и массив писем — id заявки, тема, HTML-тело,
  id шаблона, id фразы (источник: ответ в интервью №15; id фразы у каждого письма —
  опрос 2026-10-18).
- Письмо готовится без адресата: тема и тело; адрес подставит внешний сервис рассылки;
  email и ПДн не храним (источник: ответ в интервью №7; код: db/schema.sql).
- Отправки писем нет: только подготовка, отправка отдаётся наружу (mock/заглушка)
  (источник: ответ в интервью №2).
- Вход батча — сохранённые в MySQL заявки; существующий конвейер оценки заявок
  не меняется (источник: ответ в интервью №6; «Следствия»; код: db/schema.sql —
  персист заявок и решений).
- Готовые письма материализуются в `.eml` существующим в репозитории скриптом генерации
  писем; скрипт переделывается в рамках задачи под ответы интервью: получатель опционален
  (пропуск/«-» → письмо без адресата), тема и From параметризуются, тело — `text/html`,
  выходной файл — явный аргумент, вложение опционально (в письмах CASE-09 вложений нет);
  использование скрипта командой release-notes сохраняется (источник: ответ в интервью —
  «Дополнение»). Текущий интерфейс скрипта требованиям не соответствует: адресат
  обязателен, тема и From зашиты, тело `text/plain`, вложение обязательно
  (источник: код: scripts/create_email.sh).

## Open questions

Вопросы №1–15 интервью закрыты ответами заказчика в `docs/hw_grillme.md`; открытые
вопросы intent закрыты заказчиком в опросе 2026-10-18 (решения перенесены в Constraints
и «Не входит»):

1. Шаблоны (П-1 vs ответ №4): закрыт — один общий шаблон; П-1 читаем как «шаблон
   применяется к каждому из трёх решений» (Constraints).
2. id фразы в протоколе (П-4 vs №15): закрыт — П-4 буквально, id фразы обязателен
   в каждой записи; список юриста расширен на approve/review, дефолтная фраза
   помечается флагом в разрезе решения; меняет ответы №3, №5 (Constraints).
3. Тема и From: закрыт — тема рендерится тем же шаблоном; From — фиксированное значение
   проекта, точное значение в plan (Constraints).
4. Нет дефолтной фразы: закрыт — заявки пропускаются как при неполном списке; правило
   обобщено на все решения (Constraints).
5. Несколько решений по заявке: закрыт — берётся последнее решение, максимальный
   `created_at`/id (Constraints).
6. Границы зоны: закрыт — зона команды = подготовка пакета писем и протокола; реальная
   отправка — всегда внешний сервис (mock/заглушка); расхождения с формулировкой задачи
   нет («Не входит»).
7. CASE-09 — заготовка: закрыт — заполнение кейса и спека по нему — отдельный шаг
   с ведущим; intent и plan это не блокирует.

Открытых вопросов нет.

## Не входит

- Реальная отправка писем — наружу, mock/заглушка; зона команды — подготовка пакета
  писем и протокола, «сервис рассылки (зона команды)» из формулировки задачи
  трактуется как наша подготовка (источник: ответ в интервью №2; опрос 2026-10-18).
- Адресат письма, хранение email и ПДн (источник: ответ в интервью №7;
  код: db/schema.sql — email-полей нет).
- Редактирование списка фраз из системы: владелец — юрист, система только читает
  (источник: ответ в интервью №3).
- Изменение существующего конвейера оценки заявок (источник: ответ в интервью —
  «Следствия»).
- Исторические trace команды release-notes и docs/setup/commands.md (источник: ответ
  в интервью — «Дополнение»).
