# Intent MILEAGE

## Замысел

Добавить в расчёт решения по заявке проверку пробега автомобиля: если пробег составляет
400 000 км и более, решение по заявке понижается до `review` (источник: формулировка
задачи в интервью; уточнение границы — ответ заказчика 2026-09-27).

## Зачем

Заявки с очень большим пробегом несут повышенный риск, поэтому решение `approve` по ним
должно проходить ручную проверку (`review`), а не выдаваться автоматически
(источник: формулировка задачи в интервью).

## Constraints

- Порог — 400 000 км; граница строгая: `approve` остаётся только при пробеге меньше
  400 000, ровно 400 000 и выше переводится в `review` (источник: ответ заказчика
  2026-09-27 при закрытии открытых вопросов; до этого план предполагал включительную
  границу — отменено).
- Правило только ужесточает решение: понижает `approve` до `review`; базовые `review`
  и `reject` (по LTV) не меняются, `reject` не смягчается (источник: код:
  docs/plan/plan_MILEAGE.md — шаг 5, риски).
- Правило применяется после успешной валидации, к решению, уже рассчитанному по LTV;
  порядок `validate → LTV → decide` сохраняется (источник: код:
  docs/plan/plan_MILEAGE.md — шаг 3).
- Пробег не указан (отсутствие ключа, `null`, пустая строка) — ошибка валидации
  422, а не `review`; правило к таким заявкам не применяется (источник: ответ в
  интервью; код: docs/plan/plan_MILEAGE.md — шаг 8).
- Валидационная граница `max_mileage_km = 500000` — верхняя граница допустимости
  входных данных, отдельная от порога решения 400 000; не заменяется новым порогом
  (источник: код: backend/config/rules.php — vehicle.max_mileage_km; docs/plan/plan_MILEAGE.md —
  шаг 1, риски).
- Лимит по заявке после перевода в `review` нулевой, по существующей логике результата
  (источник: код: docs/plan/plan_MILEAGE.md — шаг 6).
- Порог задаётся в конфиге бизнес-правил, а не хардкодом (источник: код:
  backend/config/rules.php; docs/plan/plan_MILEAGE.md — шаг 1).
- Ответ API не дополняется причиной перевода в `review`: существующее поле
  `decision` без новых полей (источник: ответ в интервью).
- Заявка с пробегом 400 000–500 000 получает `review`, а не 422: 422 — только для
  неуказанного пробега (источник: код: docs/plan/plan_MILEAGE.md — риски;
  ответ в интервью).
- Пустая строка `''` (сейчас приводится к `0`, проходит валидацию) — ошибка 422,
  как и `null`/отсутствие ключа; требует отдельной правки валидации сверх правила
  решения (источник: ответ в интервью: «если пробег не указан это ошибка»;
  способ реализации — docs/plan/plan_MILEAGE.md).
- HTTP feature-тест на 422 в этой задаче не создаётся: достаточно unit-фиксации
  `ValidationException` в `ApplicationValidatorTest`; feature-тест отложен до
  появления изолированной инфраструктуры `tests/Feature/` (источник: ответ
  заказчика 2026-09-27 при закрытии открытых вопросов).
