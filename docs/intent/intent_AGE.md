# Intent AGE

## Замысел

Машины старше 20 лет должны сразу получать отказ: решение `reject` выносится
по возрасту до и независимо от LTV (источник: формулировка задачи заказчика
2026-10-22).

## Зачем

Очень старый автомобиль — ненадёжный залог: оценка и ликвидность с возрастом
падают, риск невозврата растёт. Такие заявки не должны проходить автоматический
`approve` даже при низком LTV и не должны требовать ручного `review` —
сразу отказ (источник: формулировка задачи заказчика 2026-10-22).

## Constraints

- Сейчас возраст > 20 лет блокируется валидацией: `ApplicationValidator`
  возвращает 422 «Возраст авто больше 20 лет», заявка не сохраняется,
  решения нет (источник: код: backend/src/Domain/ApplicationValidator.php:39-41).
- Поведение меняется на бизнес-решение: машина старше 20 лет — валидная
  заявка с `decision = reject`, `approved_limit = 0`, сохраняется в БД
  как обычная заявка; POST /api/applications → 201, POST /api/ltv → 200
  (источник: ответ заказчика 2026-10-22).
- Граница строгая: «старше 20 лет» — возраст 21 и больше → `reject`;
  ровно 20 лет — заявка обрабатывается по общим правилам LTV и пробега.
  Совпадает со справочником `ltv_by_age`, где `max_age: 20` — последняя
  допустимая ступень (источник: формулировка задачи; код:
  backend/config/rules.php:58).
- Порог — существующий ключ `vehicle.max_age_years = 20` в
  `backend/config/rules.php`, не хардкод и не новый ключ (источник: код:
  backend/config/rules.php:22).
- Проверки `min_year = 1990` и «год не в будущем» остаются в валидаторе:
  машины старше ~36 лет по-прежнему невалидны по году выпуска — 422
  (источник: код: backend/config/rules.php:21; backend/src/Domain/ApplicationValidator.php:35-38).
- Порядок `validate → расчёт LTV → решение` сохраняется; LTV рассчитывается
  и возвращается в ответе независимо от возраста (источник: код:
  backend/src/Domain/AssessmentService.php:33-34; ответ заказчика
  2026-10-22 — состав ответа не менялся).
- Правило приоритетнее LTV и пробега: `reject` по возрасту не смягчается;
  даунгрейд по пробегу понижает только `approve` до `review` и на `reject`
  не действует (источник: код: backend/src/Domain/AssessmentService.php:36-38).
- Реализация — вариант A: правило в `AssessmentService`, порог через
  конструктор как у `review_mileage_km`; `DecisionEngine` и его контракт не
  меняются (источник: ответ заказчика 2026-10-22 — выбран вариант A из
  двух предложенных).
- Ответ API без новых полей: существующее `decision = reject`, без причины
  отказа (источник: конвенция проекта — ответ заказчика по MILEAGE;
  код: backend/src/Http/ApplicationController.php:44-50).
- Схема БД не меняется: `reject` уже входит в ENUM `decisions`, миграция
  не нужна (источник: код: db/schema.sql:34).
- HTTP feature-тест в этой задаче не создаётся: в `tests/Feature/` нет
  изолированной инфраструктуры (как решено в MILEAGE 2026-09-27);
  фиксация — unit-тестами, e2e — ручная проверка.
