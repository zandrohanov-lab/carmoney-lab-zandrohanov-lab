# CASE-09 · Grill me — протокол вопросов и ответов

Кейс: `docs/sources/CASE-09.md` (массовая рассылка решений по заявкам).
Сверка с `docs/setup/code_map.md`: решение рождается в `DecisionEngine::decide()`,
персист заявок уже есть (`ApplicationRepository::save()`, таблицы `applications`,
`vehicles`, `decisions` в `db/schema.sql`). Email в схеме нет, ПДн не храним.

Intent по итогам не писали (по заданию). Вопросы задавались по одному,
только влияющие на реализацию.

## Ответы

| № | Вопрос | Ответ |
|---|--------|-------|
| 1 | Где живёт протокол «какая фраза откуда взята» (П-4)? | **A.** Записи в БД MySQL, новая таблица |
| 2 | Реальная отправка писем или подготовка? | **A.** Только подготовка: рендер + протокол в БД; отправку отдаём наружу (mock/заглушка) |
| 3 | Где живёт утверждённый список фраз отказа (П-2, владелец — юрист)? | **B.** Таблица/источник в БД, редактирует юрист, система только читает |
| 4 | Шаблоны по решениям? | **B.** Один общий шаблон для всех трёх решений; для `rejected` текст отличается только подстановкой фразы из списка |
| 5 | Откуда берётся внутренняя причина отказа для конвертации (П-3)? | **C.** Конвертации по причине нет: по решению `rejected` выбираем одну дефолтную фразу из списка |
| 6 | Источник входа батча? | **A.** Таблица заявок в MySQL (персист через `ApplicationRepository::save()` уже есть), рассылка читает её |
| 7 | Адресат письма (в схеме нет email, ПДн не храним)? | **C.** Письмо без адресата: тема + тело в пакете, адрес подставит внешний сервис рассылки |
| 8 | Как запускается батч? | **A.** HTTP-эндпоинт (например `POST /notifications/batch`) |
| 9 | Какие заявки попадают в батч? | **A.** Все `decided` с решением, по которым нет записи в протоколе (идемпотентность: одна заявка — одно письмо) |
| 10 | Где живёт единый шаблон (нужен id для П-4)? | **B.** Файл в репозитории (`backend/config/` / `templates/`), id фиксированный |
| 11 | Список фраз пуст / нет активной фразы для отказа? | **A.** Заявки с `reject` пропускаем без письма и без записи в протокол, остальные обрабатываем; в ответе — отчёт о пропущенных. Пропущенные попадут в следующий проход автоматически (записи в протоколе нет) — так решается повторная рассылка |
| 12 | Что подставляем в шаблон (персонализация)? | **A.** Минимум: id заявки, `applicant_ref`, решение (approve/review/reject), при approve — одобренный лимит; при reject — фраза из списка |
| 13 | Как выбираем дефолтную фразу для `reject`? | **B.** Фраза помечена в таблице отдельным флагом «дефолтная» |
| 14 | Формат тела письма? | **B.** HTML |
| 15 | Что возвращает эндпоинт батча? | **A.** Счётчики (обработано/пропущено по причинам) + массив писем: id заявки, тема, HTML-тело, id шаблона, id фразы (для reject) |

## Дополнение (после grill)

Готовые письма материализуем в файл `.eml` с помощью существующего скрипта
`scripts/create_email.sh`: `create_email.sh <email> <тело> <вложение> [файл .eml]` —
собирает `multipart/mixed` с телом и вложением в base64.

Расхождения скрипта с ответами grill есть, решено: скрипт переделывается по новым
требованиям в рамках реализации задачи (не сейчас). Требования к доработке:

1. Получатель опционален («-» или пропуск → письмо без адресата, ответ 7);
   сейчас скрипт требует `<email>` первым аргументом.
2. Тема и From параметризуются (ответы 12, 15); сейчас зашиты
   `Subject: Release notes` и `From: release-notes@localhost`.
3. Тело письма — `text/html` (ответ 14); сейчас скрипт пишет `text/plain`.
4. Выходной `.eml` — явным аргументом, один вызов на заявку в батче
   (ответы 8, 15); дефолтное имя по вложению больше не подходит.
5. Вложение опционально (в CASE-09 вложений нет), но поддержка сохраняется —
   скрипт используется командой release-notes.
6. При смене интерфейса обновить вызов в `.kilo/commands/release-notes.md` (шаг 5);
   исторические trace и `docs/setup/commands.md` не трогать.

## Следствия для реализации

- Новые таблицы БД (миграция схемы):
  - список фраз юриста: текст, признак активности, флаг «дефолтная», id;
  - протокол рассылки: `application_id`, `phrase_id` (для reject), `template_id`, `created_at`;
    уникальность по `application_id` — идемпотентность из ответа 9.
- Новая логика: эндпоинт `POST /notifications/batch` → отбор заявок
  (`status='decided'`, есть решение, нет записи в протоколе) → рендер одного
  общего HTML-шаблона из файла с фиксированным id → для `reject` подстановка
  дефолтной фразы из таблицы (внутренняя причина/скоринг в письмо не попадают,
  П-3) → запись протокола → ответ: счётчики + письма.
- Пропуск по `reject` при пустом/неполном списке фраз: письмо и запись в
  протокол не создаём — заявка автоматически подхватится следующим проходом.
- Отправки писем нет: эндпоинт возвращает готовый пакет, адресата не содержит.
- Существующий конвейер `AssessmentService` не меняем: решениями пользуемся
  из таблицы `decisions`.
