# План MILEAGE

## Файлы

- `backend/config/rules.php` — добавить в блок `vehicle` конфигурационный порог пробега для перевода решения в `review`; действующий `max_mileage_km` оставить без изменений.
- `backend/src/Domain/AssessmentService.php` — принять порог правила решения, после успешной валидации применить его к рассчитанному по LTV решению и передавать валидированный пробег в эту проверку.
- `backend/src/AppFactory.php` — передать в `AssessmentService` новый порог из `rules.php` при сборке приложения.
- `tests/Unit/AssessmentServiceTest.php` — передать в сервис значение порога из тестово загруженного `rules.php` и добавить проверки сочетаний LTV и пробега.
- `tests/Unit/ApplicationValidatorTest.php` — зафиксировать поведение валидации для отсутствующего `mileage`.
- `tests/Feature/ApplicationControllerTest.php` — добавить HTTP-проверку 422 для заявки без `mileage`, только если заказчик определит допустимую изолированную инфраструктуру для feature-теста с PDO/хранилищем.

## Шаги

1. В `vehicle`-разделе `backend/config/rules.php` завести отдельный порог правила решения `review_mileage_km` со значением 400000. Не менять `max_mileage_km` (500000): это верхняя граница допустимости входных данных, а не порог решения.
2. Расширить конструктор `AssessmentService`, чтобы получить порог из конфигурации; `AppFactory` должен передавать значение из `rules['vehicle']`.
3. В `AssessmentService::assess(array $payload): array` сохранить порядок `validate → calculate LTV → decide`: правило пробега выполнять только после успешной валидации, используя нормализованный `$input['mileage']`.
4. Выбрать пост-обработку в `AssessmentService`, а не изменение `DecisionEngine::decide(float $ltv): string`: сервис уже оркестрирует валидированные данные заявки, поэтому проверка гарантированно идёт после валидации, а ответственность `DecisionEngine` за LTV и его существующий контракт остаются неизменными.
5. Если базовое решение `approve` и пробег строго больше `review_mileage_km`, заменить решение на `review`; для базовых `review` и `reject` решение не менять. Таким образом правило только ужесточает решение и не смягчает `reject` по LTV.
6. Сохранить расчёт `approved_limit`: после перевода `approve` в `review` он должен стать нулевым согласно уже существующей логике результата.
7. Дополнить unit-тесты, загружая новый порог из `rules.php`, без изменения существующего захардкоженного LTV-набора в `DecisionEngineTest`.
8. Зафиксировать отсутствие ключа `mileage`: до применения правила решения валидация должна завершаться `ValidationException`, а на HTTP-границе контроллер должен вернуть 422. Поведение для строкового пустого значения не менять без решения заказчика: текущая нормализация приводит `''` к `0`, а не к ошибке.

## Тесты

- В `AssessmentServiceTest`: LTV в зоне `approve` и пробег `399999` — решение остаётся `approve`, лимит равен запрошенной сумме.
- В `AssessmentServiceTest`: LTV в зоне `approve` и пробег `400000` — решение остаётся `approve`, поскольку условие «не больше» включительно.
- В `AssessmentServiceTest`: LTV в зоне `approve` и пробег `400001` — решение меняется с `approve` на `review`, лимит равен нулю.
- В `AssessmentServiceTest`: LTV в зоне `review` и пробег `400001` — решение остаётся `review`, лимит равен нулю.
- В `AssessmentServiceTest`: LTV выше порога `reject` и пробег `400001` — решение остаётся `reject`, лимит равен нулю.
- В `ApplicationValidatorTest`: отсутствующий ключ `mileage` — `ValidationException` с ошибкой поля `mileage`.
- В `ApplicationControllerTest`: запрос без `mileage` получает HTTP 422 и ошибку `mileage`, а не `review`, при наличии согласованной feature-инфраструктуры.
- Пустой пробег: отдельно зафиксировать с заказчиком форму пустого значения. Для `null` текущее выражение с `??` даёт ошибку `mileage`; для `''` текущий `(int)` даёт `0` и не возвращает 422, поэтому тест требуемого 422 без изменения валидации добавить нельзя.
- Выполнить `make test` и `make lint`.

## Риски

- `max_mileage_km=500000` — отдельная валидационная граница: её нельзя заменить новым порогом 400000. Иначе заявки с пробегом 400001–500000 вместо `review` начнут получать 422 и не попадут в БД.
- Правило должно использовать строгое сравнение `>`; `400000` не должно переводиться в `review`.
- Ошибка порядка операций может применить правило к отсутствующему/недопустимому пробегу, обойдя 422, либо дать неверный результат для невалидных заявок.
- Ошибка при пост-обработке может смягчить LTV-`reject` до `review`; это запрещено. Также нужно проверить, что пересчитан `approved_limit`.
- Изменение конструктора `AssessmentService` затронет все места его создания; по текущему коду это `AppFactory` и unit-тест, но при реализации требуется проверить другие вызовы.
- В проекте сейчас нет `tests/Feature/` и не определена изолированная инфраструктура для HTTP-теста с `ApplicationRepository`/PDO; без неё конкретный способ фиксации HTTP 422 не установлен.
- Термин «пустой пробег» неоднозначен: поле без значения (`null`/отсутствует) отклоняется, но строка `''` приводится к `0` и принимается. Исправление этого поведения — отдельное изменение валидации, не входящее в правило решения.
- В задачу не входят изменение формы фронтенда, схемы БД, seed-данных, существующих LTV-порогов, `max_mileage_km`, возрастных правил и логики `DecisionEngine` по LTV.
