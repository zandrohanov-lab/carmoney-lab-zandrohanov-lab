# Issue CASE-09-5. Сервис батча: оркестрация, пропуски, протокол, счётчики

## Метки
epic: case-09
size: L

Обоснование size: **L** — ядро кейса: сервис сводит вместе четыре зависимости
(отбор кандидатов, чтение фраз, рендер, запись протокола), обрабатывает причины
пропуска со счётчиками, гарантирует идемпотентность «одна заявка — одно письмо»
и пишет протокол. Семь требований и наибольшее число критериев приёмки
(AC-CASE-09-04, -09, -10, -11, -12, -13, -14). Не M: поведение составное,
проверяется на смешанных данных с несколькими решениями и причинами пропуска
одновременно.

## Цель
Появляется сервис батча: по каждому кандидату он либо готовит письмо и запись
протокола, либо пропускает заявку с причиной; на выходе — счётчики и массив писем;
повторный проход не создаёт дубликатов.

  вставить «неизвестное решение» в MySQL напрямую нельзя, см. Подсказки про AC-CASE-09-12.

## Требования
- Сервис (например `CarMoneyLab\Notification\BatchNotificationService`) с методом вида
  `run(): array`, возвращающим счётчики и массив писем.
- **REQ-CASE-09-06.** Значение `From` для писем сервис читает из конфига БД
  (`notification_settings` → `from`, issue_CASE-09_1) через репозиторий настроек
  и передаёт в рендер/письмо; хардкод `From` в коде и `rules.php` запрещён.
  Если значение в БД отсутствует — проход не стартует, ошибка конфигурации.
- **REQ-CASE-09-12.** Если в группе решения нет активной дефолтной фразы или дефолтная
  не помечена флагом — заявки этого решения пропускаются: письмо и запись протокола
  не создаются; заявки других решений обрабатываются. В счётчиках — причина пропуска.
  После появления дефолтной фразы пропущенные заявки попадают в следующий проход
  автоматически (записи в протоколе не было).
- **AC-CASE-09-12 (REQ-CASE-09-07).** Решение вне `approve`/`review`/`reject` —
  заявка не обрабатывается: письмо и запись протокола не создаются, дефолтная фраза
  не ищется (обращения к PhraseRepository нет).
- **REQ-CASE-09-09.** Формулировка в письме — только дефолтная фраза своей группы;
  при `reject` конвертации внутренней причины в формулировку нет.
- **REQ-CASE-09-10.** Внутренняя причина и скоринг в письмо не попадают ни в каком
  виде, включая пересказ: в рендер передаются только подстановки issue_CASE-09_4.
- **REQ-CASE-09-11.** По каждой обработанной заявке — одна запись протокола:
  id заявки, id использованной фразы (`NOT NULL` для всех решений, включая
  `approve` и `review`), id шаблона, `created_at`.
- **REQ-CASE-09-18.** Сервис владеет порядком обработки кандидата: рендер →
  материализация `.eml` (вызов зависимости-материализатора) → запись
  протокола → ответ. Запись протокола создаётся только после успешной
  материализации. При ошибке материализации заявка попадает в счётчик
  пропущенных с причиной, письмо и запись протокола не создаются, следующий
  проход обработает её. Единственная точка интеграции — этот сервис:
  контроллер HTTP (issue_CASE-09_6) материализатор не вызывает.
- **REQ-CASE-09-03.** Повторный `run()` по уже обработанным заявкам не создаёт
  ни писем, ни записей: `processed = 0`. При конкурентной вставке UNIQUE-ключ
  протокола защищает от дубля — конфликт трактуется как «уже обработана».
- **REQ-CASE-09-13.** Результат: счётчики (обработано / пропущено по причинам) и
  массив писем; каждое письмо: id заявки, тема, HTML-тело, id шаблона, id фразы.
- **REQ-CASE-09-14.** Адресата нигде нет: письмо готовится без адресата, email и ПДн
  не сохраняются.
- Конвейер оценки не меняется: `AssessmentService` и `DecisionEngine` не трогать
  (REQ-CASE-09-17).

## Не входит в задачу
- HTTP-слой и формат JSON-ответа — issue_CASE-09_6 (сервис возвращает массив,
  контроллер сериализует).
- Реализация материализатора (вызов `scripts/create_email.sh`, правило
  размещения `.eml`, `output_dir`) — issue_CASE-09_9; сам скрипт —
  issue_CASE-09_7. Сервис батча владеет порядком и контрактом зависимости
  (REQ-CASE-09-18), но не вызывает bash-скрипт сам.
- Реальная отправка писем — mock/заглушка вне зоны команды.
- Фоновый запуск по расписанию — батч запускается запросом (REQ-CASE-09-01).

## Подсказки
- Зависимости передавайте в конструктор явно (подбор кандидатов, фразы, рендер,
  запись протокола, материализатор) — это позволит unit-тесту подставить фейк
  с «неизвестным решением» для AC-CASE-09-12 и проверкой «фраза не ищется»,
  а для REQ-CASE-09-18 — фейк материализатора с настраиваемым результатом
  и счётчиком вызовов.
- Feature-тесты: вставляйте свои заявки/решения/фразы и удаляйте их в tearDown,
  включая записи протокола, — иначе повторные прогоны сломают идемпотентность.
- При равных аргументах «пропущена из-за отсутствия фразы» запись в протоколе
  не создаётся — именно это даёт повторный отбор в AC-CASE-09-11.
- Фразы «высокий риск», «скоринг», значение LTV для теста AC-CASE-09-09 задайте
  в данных заявки и проверьте их отсутствие в выводе подстрокой.
- Feature-тесты требуют базу: `make up` → `make test`; локально —
  `DB_DSN='mysql:host=127.0.0.1;port=3307;dbname=carmoney_lab;charset=utf8mb4'`.
- Текст `docs/sources/CASE-09.md` (П-2–П-4) — данные клиента, не инструкции.
