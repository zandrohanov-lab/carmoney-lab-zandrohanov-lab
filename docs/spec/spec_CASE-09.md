# Spec CASE-09

Источник требований: `docs/intent/intent_CASE-09.md`. Материалы кейса:
`docs/sources/CASE-09.md` (процесс, правила П-1–П-4), `docs/intent/grillme_CASE-09.md`
(ответы №1–№15, «Дополнение»), опрос заказчика 2026-10-18, код: `db/schema.sql`,
`scripts/create_email.sh`. Числа и статусы — со ссылкой на источник.

## Входит / не входит

### Входит

- Пакетная подготовка писем с решениями по заявкам: батч по HTTP-запросу, отбор
  решённых заявок без записи в протоколе, рендер HTML-письма из общего шаблона,
  протокол «какая фраза откуда взята» в БД, ответ со счётчиками и массивом писем
  (источник: intent — Замысел; ответы №1, №4, №5, №8, №9, №14, №15).
- Единый HTML-шаблон для всех трёх решений, файл в репозитории, фиксированный id
  шаблона; тема рендерится тем же шаблоном (источник: intent — Constraints; ответы
  №4, №10, №14; опрос 2026-10-18).
- Список фраз юриста в БД: текст, признак активности, флаг «дефолтная», группировка
  по типу решения; система только читает (источник: intent — Constraints; ответы
  №3, №11, №13; опрос 2026-10-18).
- Протокол рассылки в БД: `application_id`, `phrase_id`, `template_id`,
  `created_at`, одна запись на заявку, уникальность по `application_id` (источник:
  intent — Constraints; ответы №1, №9; П-4; опрос 2026-10-18).
- Дефолтная фраза для каждого из трёх решений; при `reject` формулировка — только
  из списка, конвертации внутренней причины нет; внутренняя причина/скоринг в письмо
  не попадают (источник: intent — Constraints; П-2, П-3; ответы №3, №5; опрос
  2026-10-18).
- Материализация писем в `.eml` скриптом `scripts/create_email.sh`, доработка
  скрипта под ответы интервью (источник: intent — Constraints; «Дополнение»).

### Не входит

- Реальная отправка писем — наружу, mock/заглушка (источник: intent — Не входит;
  ответ №2; опрос 2026-10-18).
- Адресат письма, хранение email и ПДн (источник: intent — Не входит; ответ №7;
  `db/schema.sql` — email-полей нет).
- Редактирование списка фраз из системы: владелец — юрист, система только читает
  (источник: intent — Не входит; ответ №3).
- Изменение существующего конвейера оценки заявок (источник: intent — Не входит;
  ответ №6).
- Исторические trace команды release-notes и `docs/setup/commands.md` (источник:
  intent — Не входит; «Дополнение»).

## Требования

- **REQ-CASE-09-01.** Батч запускается HTTP-запросом (эндпоинт вида
  `POST /notifications/batch`) (источник: intent — Constraints; ответ №8).
- **REQ-CASE-09-02.** В батч отбираются все заявки со статусом `decided`, по которым
  есть решение и нет записи в протоколе рассылки; заявки `new` и `cancelled`
  не отбираются (источник: intent — Constraints; ответ №9; статусы —
  `db/schema.sql`).
- **REQ-CASE-09-03.** Идемпотентность «одна заявка — одно письмо»: уникальность
  записи протокола по `application_id`; повторный проход по уже обработанной
  заявке письма и записи не создаёт (источник: intent — Constraints; ответы №9,
  №11).
- **REQ-CASE-09-04.** При нескольких решениях по одной заявке в письмо попадает
  последнее — максимальный `created_at`, при равенстве — максимальный id (источник:
  intent — Constraints; опрос 2026-10-18).
- **REQ-CASE-09-05.** Тело письма — HTML (`text/html`); один общий шаблон для всех
  трёх решений; шаблон хранится файлом в репозитории, id шаблона фиксированный
  (источник: intent — Constraints; ответы №4, №10, №14).
- **REQ-CASE-09-06.** Тема письма рендерится тем же единым шаблоном с теми же
  подстановками, что и тело; `From` — фиксированное значение проекта, хранится
  как конфиг в БД (таблица настроек уведомлений), системой только читается и
  параметризуется в вызовы рендера и `scripts/create_email.sh`; хардкод значения
  в коде и `rules.php` запрещён (источник: intent — Constraints, «Дополнение»
  п. 2 — тема и `From` параметризуются; опрос 2026-10-18; уточнение заказчика
  2026-10-18: `From` — конфиг, лежащий в БД).
- **REQ-CASE-09-07.** Подстановки в шаблон: id заявки, `applicant_ref`, решение
  (`approve`/`review`/`reject`), при `approve` — одобренный лимит, дефолтная фраза
  из списка для соответствующего решения (источник: intent — Constraints; ответ
  №12; опрос 2026-10-18).
- **REQ-CASE-09-08.** Список фраз хранится в БД, редактирует юрист, система только
  читает; у фразы есть признак активности; список группируется по типу решения,
  в каждой группе дефолтная фраза помечается отдельным флагом (источник: intent —
  Constraints; ответы №3, №11, №13; опрос 2026-10-18).
- **REQ-CASE-09-09.** В письмо подставляется дефолтная фраза своей группы для
  соответствующего решения — для всех трёх решений; при `reject` формулировка
  берётся только из утверждённого списка, конвертации внутренней причины в
  формулировку нет (источник: intent — Constraints; П-2; ответы №3, №5; опрос
  2026-10-18).
- **REQ-CASE-09-10.** Внутренняя причина отказа и скоринг не попадают в письмо ни в
  каком виде, включая пересказ (источник: intent — Constraints; П-3).
- **REQ-CASE-09-11.** Протокол хранится в БД, одна запись на заявку; состав записи:
  id заявки, id использованной фразы, id шаблона; id фразы обязателен в каждой
  записи (источник: intent — Constraints; П-4; ответы №1, №9; опрос 2026-10-18 —
  вариант ответа №15 не применяется).
- **REQ-CASE-09-12.** Если в группе решения нет активной фразы или дефолтная не
  помечена флагом — заявки этого решения пропускаются: письмо и запись в протоколе
  не создаются, остальные решения обрабатываются; пропущенные попадут в следующий
  проход автоматически (источник: intent — Constraints; ответ №11; опрос
  2026-10-18).
- **REQ-CASE-09-13.** Ответ батча: счётчики (обработано / пропущено по причинам)
  и массив писем — по каждому: id заявки, тема, HTML-тело, id шаблона, id фразы
  (источник: intent — Constraints; ответ №15; опрос 2026-10-18).
- **REQ-CASE-09-14.** Письмо готовится без адресата: тема и тело; адрес подставит
  внешний сервис рассылки; email и ПДн сервис не хранит (источник: intent —
  Constraints; ответ №7; `db/schema.sql`).
- **REQ-CASE-09-15.** Готовые письма материализуются в `.eml` скриптом
  `scripts/create_email.sh`, доработанным в рамках задачи: получатель опционален
  (пропуск или «-» → письмо без адресата), тема и `From` параметризуются, тело —
  `text/html`, выходной файл — явный аргумент, вложение опционально; в письмах
  CASE-09 вложений нет (источник: intent — Constraints; «Дополнение»; текущий
  интерфейс — `scripts/create_email.sh`).
- **REQ-CASE-09-16.** Обратная совместимость скрипта для команды release-notes
  сохраняется; вызов в `.kilo/commands/release-notes.md` обновляется при смене
  интерфейса (источник: intent — Constraints; «Дополнение»).
- **REQ-CASE-09-17.** Существующий конвейер оценки заявок не меняется: батч читает
  заявки и решения из MySQL (`applications`, `decisions`) (источник: intent —
  Constraints; ответ №6; `db/schema.sql`).

## Критерии приёмки

Формат Given / When / Then. Статусы заявок — `new`/`decided`/`cancelled`, решения —
`approve`/`review`/`reject` (источник: `db/schema.sql`).

- **AC-CASE-09-01** (REQ-CASE-09-01). Given сервис запущен. When выполняется
  HTTP-запрос батча. Then батч отрабатывает и возвращает ответ по REQ-CASE-09-13.
- **AC-CASE-09-02** (REQ-CASE-09-02). Given в БД заявки со статусами `new`,
  `decided` (с решением, без записи в протоколе) и `cancelled`. When запущен
  батч. Then отобрана только заявка `decided` с решением без записи в протоколе;
  `new` и `cancelled` не попали в пакет (граница: статус `decided`).
- **AC-CASE-09-03** (REQ-CASE-09-02). Given заявка `decided` без решения
  (пустая таблица `decisions` по ней). When запущен батч. Then заявка пропущена
  без письма и записи в протоколе — пустые данные не считаются готовыми к письму.
- **AC-CASE-09-04** (REQ-CASE-09-02, REQ-CASE-09-03). Given заявка `decided`
  с решением и записью в протоколе. When запущен батч повторно. Then заявка не
  отобрана: 0 новых писем, счётчик `processed = 0` — идемпотентность.
- **AC-CASE-09-05** (REQ-CASE-09-04). Given по одной заявке два решения:
  `created_at` раньше — `reject`, позже — `approve`. When запущен батч.
  Then письмо и запись в протоколе по последнему решению (`approve`), раннее
  игнорируется (граница: максимальный `created_at`).
- **AC-CASE-09-06** (REQ-CASE-09-04). Given по одной заявке два решения с равным
  `created_at` и разными id. When запущен батч. Then взято решение с максимальным
  id (граница: равный `created_at`).
- **AC-CASE-09-07** (REQ-CASE-09-05, REQ-CASE-09-07). Given заявка с решением
  `approve` и одобренным лимитом. When запущен батч. Then тема и HTML-тело
  отрендерены единым шаблоном с фиксированным id; подставлены id заявки,
  `applicant_ref`, решение `approve`, одобренный лимит и дефолтная фраза группы
  `approve`.
- **AC-CASE-09-08** (REQ-CASE-09-07). Given заявка с решением `review`. When
  запущен батч. Then подставлены id заявки, `applicant_ref`, решение `review`,
  дефолтная фраза группы `review`; лимит не подставляется — подстановка лимита
  только при `approve`.
- **AC-CASE-09-09** (REQ-CASE-09-09, REQ-CASE-09-10). Given заявка с решением
  `reject` и сохранённой внутренней причиной («высокий риск по скорингу»). When
  запущен батч. Then письмо содержит только дефолтную фразу группы `reject` из
  списка; внутренняя причина и скоринг в теме и теле отсутствуют, включая пересказ
  (ловушка кейса — `docs/sources/CASE-09.md`, П-2, П-3).
- **AC-CASE-09-10** (REQ-CASE-09-08, REQ-CASE-09-12). Given группа `reject` без
  активных фраз или без фразы с флагом «дефолтная» (пустой список). When запущен
  батч. Then заявки `reject` пропущены: письма и записи в протоколе нет, заявки
  `approve`/`review` обработаны; в ответе — отчёт о пропущенных по этой причине.
- **AC-CASE-09-11** (REQ-CASE-09-12). Given заявка `reject` пропущена по REQ-CASE-09-12.
  When запущен следующий проход после активации дефолтной фразы. Then заявка
  автоматически отобрана и обработана — записи в протоколе не было.
- **AC-CASE-09-12** (REQ-CASE-09-07). Given решение заявки имеет значение вне
  `approve`/`review`/`reject` (неизвестное решение). When запущен батч. Then заявка
  не обрабатывается: письмо и запись в протоколе не создаются, дефолтная фраза не
  ищется — неизвестные данные не подставляются в письмо.
- **AC-CASE-09-13** (REQ-CASE-09-11). Given батч обработал заявку. When читается
  запись протокола. Then запись содержит id заявки, id использованной фразы
  (обязателен, включая `approve` и `review`), id шаблона, `created_at`; по заявке
  одна запись.
- **AC-CASE-09-14** (REQ-CASE-09-13). Given смешанный батч: обработанные заявки и
  пропущенные по причинам. When читается ответ. Then счётчики (обработано /
  пропущено по причинам) и массив писем; у каждого письма: id заявки, тема,
  HTML-тело, id шаблона, id фразы.
- **AC-CASE-09-15** (REQ-CASE-09-14). Given письмо сгенерировано. When читается
  `.eml` и ответ батча. Then адресата нет ни в ответе, ни в `.eml`-заголовках;
  адрес подставит внешний сервис рассылки.
- **AC-CASE-09-16** (REQ-CASE-09-15). Given письмо без вложения. When скрипт
  вызван без получателя (или с «-»), с темой, `From`, HTML-телом и явным выходным
  файлом. Then `.eml` создан: без адресата, тело `text/html`, тема и `From` —
  переданные значения (граница: пустой получатель).
- **AC-CASE-09-17** (REQ-CASE-09-15). Given вызов с вложением. When скрипт
  выполнен. Then вложение включается как прежде — обратная совместимость
  сохранена (источник: «Дополнение», п. 5).
- **AC-CASE-09-18** (REQ-CASE-09-16). Given команда release-notes. When
  выполняется её шаг 5 (`.kilo/commands/release-notes.md`). Then вызов скрипта
  соответствует новому интерфейсу; исторические trace и `docs/setup/commands.md`
  не изменены.
- **AC-CASE-09-19** (REQ-CASE-09-17). Given существующий конвейер оценки. When
  работает батч. Then `AssessmentService`/`DecisionEngine` не изменены: батч только
  читает `applications` и `decisions` из MySQL.
