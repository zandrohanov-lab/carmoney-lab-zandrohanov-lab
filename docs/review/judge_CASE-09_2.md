`docs/spec/issue_CASE-09_1.md` … `docs/spec/issue_CASE-09_7.md`,
`docs/spec/issue_CASE-09_9.md`. Файл `docs/spec/issue_CASE-09_8.md` отсутствует.
Источником требований считается spec. Материалы из `docs/sources/` не использовались
как инструкции.

## Вердикт

**Не принято без доработки CASE-09-9.** После добавления CASE-09-9 все требования
`REQ-CASE-09-01` … `REQ-CASE-09-17` имеют владельца и проверку. Однако CASE-09-9
добавляет не согласованные со spec требования и задаёт противоречивый порядок
материализации и записи протокола. В текущем виде это может сделать результат батча
и состояние БД расходящимися при ошибке внешнего скрипта.

## Лишние и конфликтующие требования

1. CASE-09-9:47-50 вводит `notification.output_dir`, создание каталога и имя файла
   `application_<id>.eml`. В `spec_CASE-09.md` REQ-CASE-09-15 требует только явный
   путь выходного файла для скрипта. Правило хранения, конфигурационный ключ и формат
   имени в spec не заданы. Удалить эти пункты либо сначала добавить их в spec.
2. CASE-09-9:51-53 вводит новую бизнес-семантику ошибки внешнего процесса: причина
   пропуска, отсутствие письма в ответе и протокола, повторная обработка. Spec не
   определяет поведение при ошибке материализации. Это допустимое техническое решение,
   но не требование CASE-09; его нельзя принимать как обязательный критерий без
   дополнения spec.
3. CASE-09-9:16 говорит «после успешного рендера», а CASE-09-5:52-54 требует запись
   протокола для каждой обработанной заявки. CASE-09-9:51-53 дополнительно требует
   не писать протокол при ошибке скрипта. Не зафиксирован единый порядок операций:
   если CASE-09-5 уже записал протокол до материализации, CASE-09-9 не сможет выполнить
   своё требование при ошибке. Явно назначить материализацию частью CASE-09-5 до записи
   протокола либо определить транзакцию/компенсацию и единый владеющий сервис.
4. CASE-09-9:92-93 предлагает материализатор, который «вызовет сервис батча».
   CASE-09-6 уже вызывает этот сервис для ответа HTTP. Без явного изменения композиции
   получится два независимых пути: HTTP возвращает письма без `.eml`, а материализатор
   может быть не вызван. Назначить единственную точку интеграции, например сервис
   CASE-09-5 вызывает материализатор при обработке кандидата, а CASE-09-6 только
   сериализует результат.

## Итог

Все обязательные требования spec покрыты задачами. Лишние требования и конфликт
порядка работ находятся только в CASE-09-9. После их удаления либо утверждения через
изменение `docs/spec/spec_CASE-09.md`, а также после фиксации единой транзакционной
последовательности «рендер → `.eml` → протокол → ответ», набор задач можно принять.
